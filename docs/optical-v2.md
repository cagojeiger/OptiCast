# OptiCast 광학 계층 v2 — 터미널 채널 재정의 (초안)

> 설계 탐색 기록이다. 확정된 결정은 [`adr/`](adr/README.md), 비트 단위 규격은 [`protocol-v2.md`](protocol-v2.md)가 기준이다.
> 이 문서의 일부 제안은 구현에서 바뀌거나 미뤄졌다. 타일 위아래 짝/홀 표시는 빠졌고(RS + CRC가 대신함),
> wasm-bindgen 대신 C ABI를 쓰며, 기본 fps는 15가 아니라 24다. `color` 프로필과 터미널 그래픽 프로토콜은 미구현이다.

v1은 "QR 한 장 = 프레임 하나 = 블록 하나"였다. 측정해 보니 이 방식에는 한계가 셋 있다.

1. **화면을 다 쓰지 못한다.** QR은 크기가 정해진 정사각형이고 고정 구조(위치 표식, 형식 정보)가 크다.
   v10 하나는 3,249모듈이지만, 200×55 터미널은 반블록으로 21,600모듈을 그릴 수 있다.
2. **찢어지면 프레임 전체를 잃는다.** 화면이 바뀌는 도중에 찍힌 사진에는 두 프레임이 섞여 있다.
   QR 하나가 화면 전체라서 섞인 줄이 한 줄만 지나가도 그 장은 버려진다.
3. **반복은 손실을 대기 시간으로 바꾼다.** 놓친 블록을 받으려면 한 바퀴를 기다려야 한다.

v2는 터미널을 하나의 광학 채널로 보고 다시 정의한다. 숫자는 `node tools/probe/tear-model.ts`와
v1 실측값에서 나왔다.

## 0. 기준: SSH로 접속한 터미널 (`ssh` 프로필)

전제: 송신 화면은 **SSH로 접속한 터미널**이다. 대역폭이 넉넉하므로 링크는 병목이 아니고,
SSH 클라이언트(Windows Terminal, PuTTY, macOS Terminal, iTerm2, Linux 터미널 등)는 UTF-8을 쓴다.
반면 색 테마, 256색이나 truecolor 지원, 서버 쪽 tmux/screen 유무는 사람마다 다르다.

그래서 기본 프로필은 **색 코드를 하나도 쓰지 않는다.** 쓰는 것은 다음 셋뿐이다.
커서 이동(`CSI r;c H`), 문자 `' '`와 `'▀'`, 반전 표시(`SGR 7`)와 해제(`SGR 0`).

```
 위 아래   쓰는 것
  0  0     ' '   보통
  1  1     ' '   반전
  1  0     '▀'   보통   (글자 = 글자색이 위, 칸 바탕 = 바탕색이 아래)
  0  1     '▀'   반전   (글자 = 바탕색이 위, 칸 바탕 = 글자색이 아래)
```

- **점 하나 = 터미널의 글자색(1) 또는 바탕색(0).** 어두운 테마든 밝은 테마든 이 두 색은 그 터미널이 낼 수 있는
  대비가 가장 큰 쌍이다(글자가 읽혀야 하니까). 어느 쪽이 밝은지는 수신기가 모서리 표식으로 판별한다.
- **아래 점은 항상 칸 바탕색이다.** 글꼴의 줄 간격도 아래 점 색으로 칠해져 줄무늬가 생기지 않는다(v1의 "배경 우선"과 같은 원리).
- **검증**: `node tools/probe/ssh-profile.ts` — 80×24와 200×55에서 어두운/밝은 테마, 줄 간격 0/3px 모두 점 오류 0.
- **비용**: 점당 ANSI 1.91 바이트(실측). 200×55는 프레임당 40 KB이고 15fps면 600 KB/s다. SSH에서는 여유가 있다.
- `▀`(U+2580)는 Windows 기본 글꼴 문자 집합(WGL4)에 들어 있어 거의 모든 고정폭 글꼴에 있다.

| 터미널 | 점 | 프레임 | 데이터/프레임 | 15fps | 1MB |
|---|---|---|---|---|---|
| 80×24 | 79×46 | 6.9 KB | 227 B | 3.2 KB/s | 5.4분 |
| 120×40 | 119×78 | 약 18 KB | 696 B | 9.9 KB/s | 1.8분 |
| **200×55** | 199×108 | 40 KB | 1,612 B | **23 KB/s** | **45초** |

**깨지는 경우와 대체 프로필.** 서버에서 tmux/screen을 UTF-8이 아닌 로캘로 띄우면 `▀`이 `_`로 바뀐다.
송신기는 `$TMUX`나 `$STY`가 있는데 로캘이 UTF-8이 아니면 경고하고 `vt100` 프로필로 내린다.
`vt100`은 공백과 반전만 쓴다(칸당 점 1개, 점당 2.85 바이트, 200×55에서 약 11 KB/s).

| 프로필 | 추가 요구 | 칸당 비트 | 대비 |
|---|---|---|---|
| **`ssh` (기본)** | UTF-8, `▀` | 2 | 1× |
| `vt100` (대체) | 없음 | 1 | 0.5× |
| `color` (선택) | `ssh` + 256색, 색 보정 | 4~6 | 2~3× |

송신기는 `--profile`로 고르고, 수신기는 프레임 헤더를 보고 자동으로 따라간다.

**SSH 경로에서 주의할 점**

- 프레임 하나(40 KB)가 TCP 패킷 여러 개로 나뉘어 도착한다. 동기화 출력(`?2026`)을 지원하지 않는 터미널은
  중간까지만 그린 화면을 보여 줄 수 있다. 이것이 2절의 "그리기 시간 P"이고, 타일 구조가 흡수한다.
- 서버 쪽 tmux/screen은 화면을 다시 그리면서 프레임을 쪼갤 수 있다. 가능하면 tmux 밖에서 실행한다.
- mosh는 중간 화면을 건너뛰고 상태만 동기화하므로 프레임이 사라질 수 있다. SSH를 쓴다.

## 1. 터미널이 그릴 수 있는 것

| 그리는 방식 | 칸당 모듈 | 모듈별 색 | 글꼴 의존 |
|---|---|---|---|
| 배경색 공백 | 1×1 | 칸마다 N색 | 없음 |
| **반블록 `▀` (배경 우선)** | 1×2 | **모듈마다 N색** | 거의 없음 (v1 검증) |
| 4분할 `▖▗▘▝…` | 2×2 | 칸당 2색만 | 중간 |
| 6분할 `🬀…` (U+1FB00) | 2×3 | 칸당 2색만 | 큼 (터미널마다 다름) |

기본은 0절의 `ssh` 프로필(반블록 + 반전, 색 코드 없음)이다.
모듈마다 색을 따로 고를 수 있는 방식은 반블록뿐이라서 `color` 프로필도 그 위에 얹는다.
비트는 공간이 아니라 색으로 늘린다.
색은 256색 팔레트의 16–231번(6×6×6 큐브, 테마가 거의 건드리지 않는다)이나 truecolor를 쓴다.
16 기본색은 사용자 테마가 바꾸므로 쓰지 않는다. 모듈당 2/4/8색이면 1/2/3비트다.

**대역폭.** 반블록 흑백은 칸당 약 8.5바이트의 ANSI가 나간다(v1 실측: v10 한 장이 16.3 KB).
데이터 1바이트에 ANSI가 약 57바이트 드는 셈이어서, pty나 SSH로 1 MB/s를 보내면 데이터는 최대 약 17 KB/s다.
화면이 크고 fps가 높으면 링크가 병목이 될 수 있다. 송신기는 `프레임 바이트 × fps ≤ 링크 대역폭`이 되도록
fps 상한을 정해야 한다.

## 2. 화면이 바뀌는 도중에 찍힌 사진

섞인 사진이 생기는 원인은 셋이다.

```
① 터미널 그리기 P   : 바이트를 해석해서 그리는 동안 화면 일부만 새 프레임
② 모니터 주사 16.7ms : 60Hz 패널이 위에서 아래로 갱신, 패널 응답 τ
③ 카메라 롤링 셔터 R : 센서가 줄 단위로 위에서 아래로 노출 (노출 시간 E)
```

모델 결과(카메라 30fps, R=20ms, E=8ms, τ=5ms). 칸의 값은 각 프레임(또는 타일 줄)이 적어도 한 번
깨끗하게 찍힌 비율이다.

| 터미널 그리기 P | 단위 | 10fps | 15fps | 20fps | 최적 |
|---|---|---|---|---|---|
| 0ms (동기화 출력 `?2026`) | 프레임 통째 | 100% | 100% | 100% | ~21장/s |
| 15ms | 프레임 통째 | 100% | 100% | 56% | ~16장/s |
| 15ms | 타일 8줄 | 100% | 100% | 95% | ~19장/s |
| 40ms (큰 화면, 느린 SSH) | 프레임 통째 | 100% | **26%** | 0% | ~11장/s |
| 40ms | 타일 8줄 | 100% | **100%** | 87% | ~19장/s |
| 80ms | 프레임 통째 | **38%** | 0% | 0% | ~7장/s |
| 80ms | 타일 8줄 | **100%** | 100% | 73% | ~17장/s |

결론:

- 동기화 출력이 되면 프레임 통째로도 30fps 카메라에서 약 20장/s까지 깨끗하다.
  이때 상한은 카메라 fps다(60fps 카메라면 약 30장/s).
- 그리기 시간이 길어지면 프레임 통째 방식은 급격히 무너진다. 프레임을 **독립적으로 검증되는 타일**로
  쪼개면, 찢어진 사진에서도 찢어진 줄이 지나간 타일만 잃는다.

```
 찢어진 사진 한 장                   v1: QR 한 장           v2: 타일 4×8
┌────────────────────────┐        ┌──────────────┐       ┌──┬──┬──┬──┐
│  프레임 n+1             │        │              │       │✓ │✓ │✓ │✓ │  n+1
│  프레임 n+1             │        │      ✗       │       ├──┼──┼──┼──┤
│~~~~~~ 섞인 줄 ~~~~~~~~~~~│   →    │   전부 버림   │       │✗ │✗ │✗ │✗ │  섞임
│  프레임 n               │        │   (0 / 1)    │       ├──┼──┼──┼──┤
│  프레임 n               │        │              │       │✓ │✓ │✓ │✓ │  n
└────────────────────────┘        └──────────────┘       └──┴──┴──┴──┘
                                                          28 / 32 사용
```

폰을 90° 돌리면 롤링 셔터는 화면의 가로 방향으로 쓸고 지나간다. 그래서 타일은 가로 줄이 아니라 2D 격자로 둔다.

## 3. 터미널로 보낼 수 있는 최대량

```
초당 데이터 = 모듈 수 × 모듈당 비트 × η(0.6) × 유효 fps(15) × 파운틴 효율(0.95) / 8
```

η는 모서리 표식, 타일 헤더, 내부 RS, CRC를 빼고 남는 비율이다.

아래 표의 흑백 열이 기본 `ssh` 프로필이다. 4색과 8색 열은 `color` 프로필이다.

| 터미널 | 모듈 (반블록) | 흑백 | 4색 | 8색 | 1MB (흑백) |
|---|---|---|---|---|---|
| 80×24 | 80×46 | 3.9 KB/s | 7.9 KB/s | 12 KB/s | 4.5분 |
| 200×55 | 200×108 | **23 KB/s** | **46 KB/s** | 69 KB/s | **45초** |
| 320×90 | 320×178 | 61 KB/s | 122 KB/s | (카메라 한계) | 17초 |

비교: v1(QR v10, 2fps)은 1MB 한 바퀴에 49분이 걸린다.

- **물리 상한**: 320×178모듈 × 3비트 × 60Hz는 약 1.3 MB/s다. 카메라 fps, 찢어짐, ECC 때문에 실제로는 도달할 수 없다.
- **카메라 한계**: 1080p 영상에서 화면이 80%를 채우고 모듈당 4~5px이 필요하면 약 300×170모듈이다.
  320×90 터미널이 이미 이 한계에 걸린다.
- **현실 목표**: 200×55 흑백 약 20 KB/s(1MB에 1분 이내). 확장 목표는 4색 약 40 KB/s.

## 4. v2 정의

### 4.1 전송 단위는 타일, 프레임은 타일을 담는 그릇

```
┌▣──────────────────────────────▣┐   ▣ 모서리 표식 (프레임당 4개, QR처럼 심볼마다 두지 않는다)
│ ▒▒▒▒ 색 보정 패치 · 타이밍 줄 ▒▒│   ▒ 매 프레임 팔레트 기준색, 모듈 격자 정렬용
│ ┌────┐┌────┐┌────┐┌────┐       │
│ │타일 ││타일 ││타일 ││META│      │   타일 = [transfer id 2B][symbol id 3B][payload][CRC-32] + RS
│ └────┘└────┘└────┘└────┘       │   위/아래 테두리에 프레임 패리티(짝/홀)를 표시한다
│   …        (예: 4열 × 8행)       │   → 위아래가 다르면 찢어진 타일이므로 디코딩 전에 버린다
└▣──────────────────────────────▣┘
```

- 타일은 세로 8행 이상으로 나눈다(찢어짐 한 번이 지우는 몫 ≤ 1/8). 타일 하나의 payload는 128 B 이상이 되게 한다.
- META는 타일 하나로 만들어 매 프레임 넣는다(32타일이면 3%). v1처럼 프레임 한 장을 통째로 쓰면 9%다.

### 4.2 부호화는 체계적 파운틴

```
심볼 id 0 … N-1   원본 블록 그대로       → 손실이 없으면 v1처럼 한 바퀴에 끝난다
심볼 id N …       복구 심볼, 매번 새로 생성  → 받은 프레임 중 버려지는 것이 없다
```

수신기는 **아무 심볼이나 N + α개** 모으면 복원하고 SHA-256으로 검증한다.
후보는 RaptorQ(RFC 6330) 계열이다. 더 단순한 대안은 LT 부호와 가우스 소거다.
모델에서 5378블록 기준으로 반복은 2.96바퀴, 파운틴은 1.05바퀴가 걸렸다(손실 5%, 2.8배). 손실 20%에서는 3.3배였다.

### 4.3 렌더링 규칙

- 기본(`ssh`): `▀`과 공백, 반전(`SGR 7` / `SGR 0`)만 쓴다. 아래 점 = 칸 바탕(배경 우선). 같은 값이 이어지면 SGR을 생략하고,
  행마다 `CUP`로 시작한다. `color`: 같은 배치에 256색 큐브(16–231)를 쓴다.
  한 프레임은 행 순서대로 한 번의 `write`로 쓴다.
- 동기화 출력 `?2026`. 지원하는 터미널은 화면을 원자적으로 교체하고, 지원하지 않으면 타일이 흡수한다.
- fps 상한 = min(카메라가 받쳐 주는 값, 링크 대역폭 ÷ 프레임 바이트).
- 주기마다 무늬를 바꾼다(v1의 마스크 회전과 같은 이유). 파운틴에서는 복구 심볼이 매번 다르므로 자연스럽게 해결된다.

### 4.4 수신 파이프라인

1. 첫 프레임에서 모서리 표식을 전역 탐색해 호모그래피를 구한다.
2. 이후 프레임은 직전 위치 근처만 추적한다. QR처럼 매번 처음부터 찾지 않는다.
3. 모듈 중심에서 샘플링하고, 보정 패치를 기준으로 색을 분류한다.
4. 타일마다 패리티 일치 → RS → CRC를 거쳐 심볼을 저장한다(중복 제거).
5. N + α 심볼이 모이면 파운틴으로 복원하고 SHA-256으로 검증한다.

QR 검출 대신 정해진 2만여 점을 샘플링하므로 장당 디코딩 비용이 작다.
RS와 파운틴 연산은 WASM으로 구현한다.

### 4.5 주기와 전송량 예시 (200×55, `ssh` 프로필, 15fps)

v1의 "같은 프레임을 반복하는 주기"는 없어진다. 원본 조각을 한 번 다 보여 주는 시간(원본 패스)만 남고,
그 뒤로는 매 프레임 새로운 복구 조각이 나온다.

```
프레임 1장 = 타일 16개 = 데이터 조각 15개(100 B씩) + META 1개   → 1,500 B/프레임
1 MB = 원본 조각 10,486개 → 700프레임 → 15fps에서 46.7초 (원본 패스)
그 뒤: 복구 조각 10,486번부터 계속 새로 생성 (RaptorQ 조각 번호는 24비트라 약 20시간 동안 겹치지 않는다)
수신 완료 = 아무 조각이나 10,488개 → 손실 0%: 46.6초 · 10%: 51.8초 · 20%: 58.3초 (합류한 시점부터)
```

수신 화면의 안내는 "다음 바퀴를 기다리세요"가 아니라 "조각 6,120 / 10,488 · 약 19초 남음"이 된다.
들어오는 조각 속도가 일정해서 남은 시간을 바로 계산할 수 있다.

**늦게 합류해도 된다 (시작 시각을 몰라도 된다).** 타일마다 [전송 ID][조각 번호][데이터][CRC]가 들어 있고
META도 매 프레임 실리므로, 수신기는 그 전에 무엇이 나갔는지 알 필요가 없다. 실측(`raptorq` 2.0.1, 1 MiB, 100 B 조각):

| 합류 시점 | 받은 것 | 결과 |
|---|---|---|
| 1시간 뒤 (조각 번호 810,000부터), 손실 0% | 복구 조각 10,923개 | 정확히 복원 |
| 1시간 뒤, 손실 10% | 복구 조각 10,923개 | 정확히 복원 |
| 10시간 뒤 (8,100,000부터), 손실 10% | 복구 조각 10,923개 | 정확히 복원 |

- 원본 조각 없이 복구 조각만 받아도 K개에서 복원된다. 이 문단의 이전 판은 "437개(4%) 더 필요"라고 적었는데 계산 실수였다.
  조각 크기 100을 지정해도 정렬 8 때문에 실제 조각은 96바이트라 K = 10,923이었고, 위 표의 "10,923개"가 곧 K였다.
  K = 100 ~ 175,919에서 다시 잰 결과는 [ADR 0006](adr/0006-raptorq-fountain.md)에 있다(복구 조각만으로 추가 0개).
- 조각 번호는 24비트라 초당 225개면 약 20.7시간 뒤에 한 바퀴 돈다. 그 뒤에도 동작하며, 중복은 조각 번호로 걸러진다.
- 송신기를 다시 켜도 전송 ID(파일 해시 + 설정)가 같으므로 재시작 전후의 조각을 합칠 수 있다.
  재시작할 때는 복구 조각 시작 번호를 무작위로 골라 중복을 피한다.
- 받은 조각을 브라우저 저장소(IndexedDB)에 보관하면 여러 번 나눠 찍어도 이어진다(세션 재개).

## 5. 실기기에서 측정할 값

| 값 | 왜 필요한가 |
|---|---|
| P (터미널·SSH 조합별 그리기 시간) | 타일 줄 수와 fps 상한 결정 |
| R, E (폰 롤링 셔터, 노출) | 찢어짐 모델 보정 |
| 색 수별 모듈 오류율 | 2/4/8색 선택, RS 강도 |
| 모듈당 필요 px | 터미널 크기 상한 |

## 6. 추천 구현

| 계층 | 선택 | 근거 |
|---|---|---|
| 파일 무결성 | SHA-256 | v1 유지. 정확히 같은 파일이 아니면 내놓지 않는다 |
| 프레임 간 부호 | **RaptorQ (RFC 6330)**, Rust `raptorq` 2.0.1 | 실측: 1 MiB를 128 B 심볼 8192개로 나누고 10%를 잃어도 받은 8192개로 복원(추가 0개). wasm32 디코딩 44 ms, 네이티브 10 ms |
| 타일 안 부호 | Reed–Solomon GF(2^8), 오류·소실 동시 복호 | 경계값 근처의 애매한 모듈을 소실로 표시해 정정 능력을 2배로 쓴다 |
| 타일 검증 | 위아래 패리티 표시 + CRC-32C | 찢어진 타일을 RS 전에 버리고, RS가 잘못 고친 경우도 걸러 낸다 |
| 화면 | 기본 `ssh`(`▀` + 반전, 색 코드 없음), 대체 `vt100`, 선택 `color`. `?2026`, 한 번의 `write` | 테마·색 지원과 무관, 실측 점 오류 0 |
| 수신 | rVFC → Worker → WASM(추적·샘플·색 분류·RS·RaptorQ) | 장당 처리 비용이 작아 30fps 카메라 프레임을 전부 처리할 수 있다 |

코어는 Rust 하나로 만들고 양쪽이 공유한다. v1에서 TypeScript를 공유한 것과 같은 원리다.

```
crates/core   배치·RS·RaptorQ·CRC·SHA-256 (I/O 없음)
crates/cli    송신: 정적 바이너리 하나 (격리 서버에 Node 없이 반입)
crates/wasm   수신 디코더 (wasm-bindgen)
web/          수신 UI (현재 TS·Vite 재사용, 오프라인 PWA)
tools/        시뮬레이터·e2e (현재 TS 재사용)
```

## 7. 단계

1. **파운틴 부호** — v1의 QR 위에서도 바로 실효 약 2.7배. 이후 모든 단계의 기반이다.
2. **`ssh` 프로필 격자와 타일** — `▀` + 반전. 시뮬레이터에 점진적 그리기(TCP로 나뉘어 도착)와 롤링 셔터를 넣어
   검증한다(현재 e2e의 "QR마다 첫 장은 반쯤 섞임"은 단순화된 모델이다). 목표는 200×55 15fps에서 20 KB/s 이상.
3. **`vt100` 대체 프로필** — 같은 격자 코드에서 칸당 점 수만 바뀐다. tmux와 비UTF-8 로캘을 감지해 자동으로 내린다.
4. **`color` 프로필** — 4색부터 시작해 8색으로 간다.
5. **(선택) 터미널 그래픽 프로토콜** — sixel, kitty, iTerm2를 지원하면 글자 칸 제약 없이 그린다.
