# ADR 0007: META 타일, 내용 기반 전송 ID, 선택적 압축

- Status: Accepted
- Date: 2026-11-01

## Context

언제 합류할지 모르는 수신기가 복원을 시작하려면 파일 크기, 해시, RaptorQ 파라미터(OTI), 이름을 알아야 한다.
같은 화면에 다른 전송이 보여도 섞이면 안 된다. 그리고 송신기를 다시 켜더라도 앞서 받은 조각을 계속 쓸 수 있으면 좋다.

## Decision

- **META**는 타일 내용 96바이트에 담는다.

  | 크기 | 내용 |
  |---|---|
  | 4 | 전송 ID = CRC-32C(META[4..96]) |
  | 8 | 원본 크기 |
  | 32 | 원본 SHA-256 |
  | 1 | 압축(0 = 없음, 1 = deflate-raw) |
  | 12 | RaptorQ OTI(RFC 6330 직렬화) |
  | 1 + 38 | 파일 이름 길이와 UTF-8 이름 |

- **간격**: m = max(1, ⌈10 / N⌉) 프레임마다 META를 하나 넣는다. 위치는 타일 f mod N으로 돌린다(반사광처럼 같은 자리에서만
  잃는 일을 피한다). 타일이 10개 이상이면 매 프레임 들어간다.
- 모든 타일에 **태그** = 전송 ID 하위 16비트를 싣는다. 수신기는 META로 ID를 확정한 뒤, 다른 ID는 "다른 전송"으로만 센다.
- **전송 ID는 내용과 설정에만 의존**한다(시각이나 난수가 들어가지 않는다). 같은 파일을 같은 설정으로 다시 보내면 같은 ID가 나온다.
- **압축**: deflate-raw(`flate2`, 순수 Rust 백엔드)를 시도해서 원본보다 작아질 때만 쓴다.
- **이름**: 경로를 뺀 기본 이름만 쓴다. 38바이트를 넘으면 확장자를 살리고 그 앞부분을 UTF-8 문자 경계에서 자른다.
  수신기는 저장할 때 이름을 다시 정리한다(경로 문자 제거).
- **빈 파일**: OTI를 모두 0으로 두고 모든 타일을 META로 채운다. 수신기는 META만으로 완료한다.

## Rationale

대안과 선택 이유:

- **첫 프레임에만 헤더**: 늦게 합류한 수신기는 영원히 모른다.
- **META를 프레임 한 장 전체로(v1, 10프레임마다)**: 오버헤드가 9%다. 타일 하나면 19타일 화면에서 약 5%이고, 화면이 클수록 준다.
- **실행마다 무작위 전송 ID**: 송신기를 다시 켤 때마다 ID가 바뀌어 앞 조각과 폰의 이어 받기 저장분을 버려야 한다.
- **SHA-256 앞부분을 ID로**: 같은 파일이라도 압축 여부나 OTI가 다르면 조각이 호환되지 않는데 ID는 같아진다.
  META 전체에 대한 CRC라야 "조각을 섞어도 되는가"와 일치한다.
- **항상 압축**: 이미 압축된 입력(tar.gz, 영상)은 오히려 커진다.
- **zstd**: 압축률은 더 좋지만 WASM 디코더 크기와 의존성이 는다. deflate는 순수 Rust 구현이 작고 어디서나 빌드된다.

## Consequences

- META를 놓쳐도 다음 프레임에 또 온다. 합류 직후 바로 파일 이름, 크기, ID가 보인다(송신 상태 줄의 `id`와 대조 가능).
- 실기기 test.tar.gz는 deflate로 16.9 MB → 16.4 MB(3%)만 줄었다. 이미 압축된 입력이라 그렇다.
- 16비트 태그가 우연히 같은 다른 전송(확률 1/65,536)이 계속 보이면 완료가 늦어지는 문제가 남아 있다.
  잘못된 파일이 저장되는 일은 SHA-256이 막는다.
