# ADR 0006: 타일 간 소실 복구 — RaptorQ 체계적 파운틴

- Status: Accepted
- Date: 2026-11-01

## Context

프레임 단위 손실은 피할 수 없다. 찢어진 프레임, 화면 밖으로 나간 부분, 흔들림, 초점, 처리가 밀려 건너뛴 프레임 때문이다.
단방향 채널([0001](0001-one-way-optical-channel.md))이라 "3번 조각을 다시 보내 줘"라고 요청할 수 없다.

v1은 같은 프레임을 주기적으로 반복했다. 반복은 손실을 대기 시간으로 바꾼다. 마지막 몇 블록을 기다리느라 여러 바퀴가 걸리고,
고정된 자세에서 특정 프레임이 계속 실패하면 아예 끝나지 않는다.

## Decision

- **RaptorQ**(RFC 6330), `raptorq` =2.0.1을 쓴다. 조각 크기 T = 96바이트(타일 내용), 정렬 8.
- 블록 분할은 `ObjectTransmissionInformation::with_defaults`를 따른다. Z = ⌈K / 56,403⌉, 블록마다 따로 복원한다.
  블록은 최대 255개이므로 파일은 약 1.38 GB까지다.
- 송신 순서:
  1. **원본 패스**: 모든 블록의 원본 조각(ESI < K_b)을 블록을 돌아가며 한 번씩 보낸다. 손실이 없으면 한 바퀴에 끝난다(체계적 부호).
  2. **복구 조각**: 그다음부터는 ESI = K_b + r₀ + i인 복구 조각을 끝없이 새로 만든다. r₀는 실행마다 고르는 [0, 2²⁰) 범위의 난수이고,
     ESI가 2²⁴에 닿으면 K_b로 돌아간다.
- 수신기는 (SBN, ESI)로 중복을 지우고 블록마다 디코더에 넣는다. 화면 안내는 K + 2개를 기준으로 한다.

### 빠진 조각이 채워지는 원리

복구 조각 하나는 여러 원본 조각을 섞은 것이다(XOR과 GF(2⁸) 곱의 선형 결합). 어떤 조각을 섞을지는 조각 번호로 정해지는
의사 난수 규칙이라, 송신기와 수신기가 번호만으로 같은 조합을 계산한다. 그래서 타일에는 번호만 싣는다.

```
원본 1바퀴:  [1][2][3][4][5][6]
폰이 받음:   [1][ ][3][4][ ][6]      ← 2, 5 놓침
복구 조각:   R7 = 1⊕2⊕4   R9 = 1⊕5   …   (번호마다 다른 조합, 끝없이)
폰:          2 = R7⊕1⊕4,   5 = R9⊕1
```

수신기 입장에서 원본 조각 K개는 미지수이고, 받은 조각 하나하나가 방정식이다. 서로 다른 조각이 K개쯤 모이면 연립방정식을 풀어
빠진 원본을 모두 계산한다. 어떤 조각을 놓쳤는지는 상관없고 **개수만** 중요하다.

## Rationale

대안과 선택 이유:

- **단순 반복(v1)**: 손실률 p에서 L바퀴 뒤 K개를 모두 모았을 확률은 (1 − p^L)^K다. K = 171,012, p = 10%면 99% 완료에 약 7~8바퀴가 걸린다.
  파운틴은 (K + 2) / (1 − p), 즉 약 1.11바퀴다. 모델(5,378블록)에서는 손실 5%에 2.96바퀴 대 1.05바퀴(2.8배), 손실 20%에 3.3배였다.
- **프레임 간 RS 소실 부호(인터리빙)**: 부호율을 미리 정해야 하고, 그보다 많이 잃으면 실패한다. 조각을 끝없이 새로 만들 수 없다.
- **LT 부호 + 가우스 소거**: 단순하지만 수~수십 %의 추가 조각과 큰 디코딩 비용이 든다.
- **Wirehair**(libcimbar가 씀): 성능은 좋지만 C++ 라이브러리라 Rust/WASM 통합 부담이 있다.
- **RaptorQ** (채택): RFC 6330 기준 K + 2개를 받으면 복원 실패 확률이 약 10⁻⁶이다. 인코딩과 디코딩이 K에 거의 비례하고,
  순수 Rust 크레이트가 wasm32로 빌드되며 Apache-2.0이다.

측정(`raptorq` 2.0.1, T = 96):
- **원본을 하나도 못 받고 복구 조각만 받아도 K개에서 풀린다.** K = 100 / 1,000 / 10,923 / 42,753에서 343회 실험했고,
  모두 복구 조각 정확히 K개에서 복원했다(추가 0개). 원본 10% 손실 + 복구 조각을 섞어도 최대 +1개였다.
  16,888,158바이트(4블록, K = 175,919)도 복구 조각만으로 추가 0개였다.
- 1시간 뒤(조각 번호 약 810,000), 10시간 뒤(약 8,100,000)에 합류하고 손실이 10%여도 정확히 복원했다.
- 예전 기록 "복구 조각만이면 +437개"는 계산 실수였다. 조각 크기 100을 지정했지만 정렬 8 때문에 실제로는 96이 되어
  K = 10,923이었는데, K를 1 MiB ÷ 100 = 10,486으로 계산했다.

## Consequences

- 수신 시간은 "서로 다른 조각 K + 2개 ÷ 초당 받는 조각 수"로 미리 계산된다. 송신 상태 줄의 `phone needs ~Ns of view`가 이것이다.
- 언제 합류해도 되고, 원본 패스를 통째로 놓쳐도 손해가 없다.
- 송신기를 다시 켜도 r₀가 달라서 앞 실행과 겹치지 않는 조각이 나온다. 전송 ID가 같으면
  ([0007](0007-meta-tile-and-transfer-id.md)) 두 실행의 조각을 합칠 수 있다.
- 수신기는 블록 전체를 메모리에 들고 있어야 한다. 그래서 크기 상한이 필요하다([0010](0010-receiver-safety-and-resume.md)).
- 조각을 만드는 규칙이 버전마다 바뀌면 송수신 호환이 깨지므로 크레이트 버전을 `=2.0.1`로 고정한다.
