# ADR 0002: 화면 인코딩 — `▀` 반블록과 반전만 쓰고 색 코드는 쓰지 않는다

- Status: Accepted
- Date: 2026-11-01

## Context

터미널이 그릴 수 있는 것은 글자와 글자색, 바탕색뿐이다. SSH 클라이언트는 Windows Terminal, PuTTY, macOS Terminal,
iTerm2, 리눅스 터미널 등 제각각이다. 색 테마, 256색이나 truecolor 지원 여부, 서버 쪽 tmux/screen 사용 여부도 사람마다 다르다.

질문은 하나다. 어떤 터미널에서도 같은 결과로, 한 칸에 몇 비트를 그릴 수 있는가.

## Decision

기본 `ssh` 프로필은 다음만 쓴다. 커서 이동(`CSI r;c H`), 문자 `' '`와 `'▀'`(U+2580), 반전 `SGR 7`과 해제 `SGR 0`(`ESC[m`).
칸 하나에 위·아래 모듈 2개를 담는다.

```
 위 아래   출력
  0  0     ' '   보통
  1  1     ' '   반전
  1  0     '▀'   보통   (글자 = 글자색이 위, 칸 바탕 = 바탕색이 아래)
  0  1     '▀'   반전   (글자 = 바탕색이 위, 칸 바탕 = 글자색이 아래)
```

- 모듈 1은 그 터미널의 글자색, 0은 바탕색이다.
- 아래 모듈은 항상 칸 바탕색으로 그린다("배경 우선"). 글꼴의 줄 간격도 아래 모듈 색으로 칠해지므로 줄무늬가 생기지 않는다.
- 격자 크기: W = min(C − 1, 511), H = min(2·(R − 2), 510). 아래 2줄은 상태 줄이다. 마지막 열은 비워 둔다
  (마지막 열에 쓰면 터미널이 자동 줄바꿈 대기 상태가 된다).
- SGR은 값이 바뀔 때만 보내고, 행마다 `CUP`로 시작한다.
- 대체 `vt100` 프로필은 공백과 반전만 쓴다(칸당 모듈 1개). `$TMUX`나 `$STY`가 있는데 로캘이 UTF-8이 아니면
  자동으로 고른다. 이 경우 `▀`가 `_`로 깨지기 때문이다.

## Rationale

대안과 선택 이유:

- **배경색 공백만(칸당 모듈 1개)**: 글꼴과 무관하지만 밀도가 절반이다. `vt100` 대체 프로필로만 쓴다.
- **4분할·6분할 블록(`▖▗▘▝`, U+1FB00)**: 칸당 모듈은 많지만 칸 하나에 두 색만 쓸 수 있고, 글꼴과 터미널마다 모양이 다르다.
  6분할은 지원 편차가 특히 크다.
- **점자(`⠿`, 2×4)**: 점 사이에 빈틈이 있어 이진 격자로 읽기 어렵고 글꼴 의존이 크다.
- **256색·truecolor로 모듈당 2~3비트**: 용량은 2~3배지만 테마, 색 지원, 카메라 색 보정에 의존한다. 같은 배치 위에 얹을
  `color` 프로필 후보로 남긴다(미구현).
- **16 기본색**: 사용자 테마가 바꿔 버린다.
- **반블록 + 반전** (채택): 글자색과 바탕색은 어떤 테마에서든 그 터미널이 내는 대비가 가장 큰 쌍이다(글자가 읽혀야 하니까).
  어느 쪽이 밝은지는 수신기가 위치 표식을 보고 판별한다. `▀`는 Windows 기본 문자 집합(WGL4)에 들어 있어 거의 모든
  고정폭 글꼴에 있다.

측정: `node tools/probe/ssh-profile.ts`로 80×24와 200×55, 어두운·밝은 테마, 줄 간격 0/3px를 모두 그려 봤고 모듈 오류는 0이었다.
ANSI 비용은 모듈당 1.91바이트라 200×55 프레임이 약 40 KB다. 24fps면 약 1 MB/s로, SSH 대역폭에 여유가 있다.

## Consequences

- 모듈당 1비트다. 용량은 화면 크기에 비례한다(200×55에서 데이터는 프레임당 1.73 KB).
- 극성(밝은 글자인지 어두운 글자인지)을 미리 모르므로 수신기는 두 극성 모두에서 표식을 찾는다.
- 서버 쪽 tmux는 화면을 다시 그리면서 프레임을 쪼갤 수 있으니 가능하면 tmux 밖에서 실행한다. mosh는 중간 화면을
  건너뛰므로 쓸 수 없다.
- 색 프로필은 같은 배치와 타일 위에 칸당 비트 수만 바꿔 얹을 수 있다.
