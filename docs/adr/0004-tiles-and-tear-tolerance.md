# ADR 0004: 타일 단위 전송, 찢어짐 대응, 기본 24fps

- Status: Accepted
- Date: 2026-11-01

## Context

화면이 바뀌는 도중 찍힌 사진에는 두 프레임이 섞인다. 원인은 셋이다.

1. 터미널이 그리는 시간 P. SSH로 40 KB 프레임이 TCP 패킷 여러 개로 나뉘어 도착한다.
2. 모니터 주사 16.7 ms(60 Hz).
3. 카메라 롤링 셔터. 센서가 줄 단위로 위에서 아래로 노출한다.

모델(`tools/probe/tear-model.ts`, 카메라 30fps, 롤링 셔터 20 ms)에서 P = 40 ms일 때 프레임 통째 방식은
15fps에서 프레임의 26%만 깨끗하게 찍혔다. 8줄로 나눈 타일 방식은 100%였다.

## Decision

- 전송 단위는 **타일**(1024모듈 = 128바이트)이다. 타일마다 따로 검증한다([0005](0005-tile-error-correction.md)).
  프레임은 타일을 담는 그릇일 뿐이다.
- 찢어진 사진에서도 섞인 줄이 지나간 타일만 버린다. 위쪽(새 프레임) 타일과 아래쪽(이전 프레임) 타일은 모두 유효한 조각으로 쓴다.
- 프레임은 동기화 출력(`ESC[?2026h … ESC[?2026l`) 안에서 **한 번의 write**로 보낸다. 지원하는 터미널은 화면을 통째로 바꾸고,
  지원하지 않으면 타일 구조가 찢어짐을 흡수한다.
- 배치나 터미널 크기가 바뀌면 같은 write 안에서 `ESC[2J`로 지운 뒤 새 배치로 그린다.
- 기본은 **24fps**다. 2·3·5·8·10·12·15·20·24·30 단계로 바꿀 수 있다. 30을 고르면 경고한다.
- 쓰기가 늦어지면 몰아서 따라잡지 않는다. 다음 프레임은 지금부터 한 주기 뒤다.

## Rationale

대안과 선택 이유:

- **프레임 통째 + CRC**: 찢어지면 그 장은 0이다.
- **프레임 사이 빈 화면, 같은 프레임 두 번**: 찢어짐은 줄지만 처리량이 절반이다.
- **타일 위아래 테두리에 프레임 짝/홀 표시**(optical-v2 초안): RS와 CRC가 섞인 타일을 이미 걸러 내므로 구현에서 뺐다. 모듈을 아낀다.
- **24fps 기본**: 아이폰 카메라는 보통 30fps다. 송신 fps가 카메라 fps와 같으면 위상이 고정되어, 매번 같은 순간(다시 그리는 중)에
  찍힐 수 있다. 24는 카메라 5장에 송신 4장꼴이라 찍히는 위상이 계속 미끄러진다. 60fps 카메라라면 30까지 쓸 수 있다.
- **2D 격자 타일**: 폰을 90° 돌리면 롤링 셔터가 화면의 가로 방향으로 지나간다. 가로 줄로만 나누면 그때 무너진다.

## Consequences

- e2e(가상 카메라, 찢어진 캡처 40%)에서 타일 인식률 99%였다.
- 타일로 나누고 남는 데이터 모듈은 백색화 비트열로 채운다.
- 상태 줄은 실제로 쓴 fps를 재서 목표와 다르면 `24/11 fps`처럼 보여 준다. SSH가 느린 경우를 드러낸다.
- 전송 중 크기를 바꿔도 된다. 조각 번호와 전송 ID는 배치와 무관하다(e2e: 200×55 ↔ 160×45, 120×40 ↔ 200×55 통과).
